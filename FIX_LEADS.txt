FIX: "LEADS TABLE NOT RECORDING ANY EMAIL"
==========================================

Why you saw nothing: the old function logged database errors but still
returned success, so the site looked fine while nothing saved. This
build now RETURNS the real error, so you can see exactly what's wrong.
Work down this list — it's almost always #1 or #2.


1) DID YOU RUN THE MIGRATION? (most common cause)
   The `leads` table has to exist. In Supabase:
     - Left sidebar → SQL Editor → New query
     - Paste the entire contents of:  supabase/migrations/0001_leads.sql
     - Run it.
   Then check: Table Editor → you should see a `leads` table.

   If the table wasn't there, that was it. Test an opt-in again.


2) ARE THE EDGE FUNCTIONS DEPLOYED?
   The site calls a function called `subscribe`. It must be live.
     supabase login
     supabase link --project-ref YOUR-PROJECT-REF
     supabase functions deploy subscribe
     supabase functions deploy verify-payment
   In Supabase → Edge Functions you should see both listed.


3) ARE THE PUBLIC KEYS IN lib/site.ts? (or Vercel env + REDEPLOY)
   Open lib/site.ts and confirm these are your REAL values, not the
   "PASTE_YOUR_..." placeholders:
     SUPABASE_URL       = "https://xxxx.supabase.co"
     SUPABASE_ANON_KEY  = "eyJ...."
   If they're still placeholders, the site skips the call entirely
   (you'll see a console warning "Supabase not set"). Paste them and
   redeploy.


4) READ THE ACTUAL ERROR (this build now shows it)
   Open your live site, press F12 → Network tab, submit the opt-in.
   Click the "subscribe" request → Response. You'll see one of:
     - {"stage":"database","error":"...relation \"leads\" does not
        exist..."}  → run the migration (step 1).
     - {"stage":"config","error":"...missing credentials..."}  →
        redeploy the function (step 2).
     - {"ok":true}  → it saved! Check Table Editor → leads.

   Also check the function logs: Supabase → Edge Functions → subscribe
   → Logs. Any red error there names the exact problem.


5) STILL NOTHING? CHECK THE TABLE NAME + RLS
   - The table must be named exactly  leads  (lowercase).
   - RLS being ON is fine — the function uses the service-role key,
     which bypasses RLS. Do NOT add public policies; you don't need
     them, and the migration is already correct.


QUICK TEST WITHOUT THE WEBSITE
------------------------------
You can hit the function directly to isolate the problem. In a terminal
(replace the URL + anon key):

  curl -i -X POST \
    "https://YOUR-PROJECT.supabase.co/functions/v1/subscribe" \
    -H "Content-Type: application/json" \
    -H "Authorization: Bearer YOUR_ANON_KEY" \
    -H "apikey: YOUR_ANON_KEY" \
    -d '{"name":"Test","email":"test@example.com"}'

  - 200 {"ok":true}  → saving works; check Table Editor → leads.
  - 500 {...error...} → the message tells you which step above to fix.
